What the Unix epoch is

Epoch time counts the seconds elapsed since 00:00:00 UTC on 1 January 1970, ignoring leap seconds. It is the default timestamp representation in Unix, in most databases, and in nearly every JSON API. Because it is an absolute instant with no timezone attached, it is unambiguous — unlike "2026-01-01 09:00", which means different moments depending on where you are standing.

Seconds, milliseconds, or something else

The classic failure mode is passing milliseconds where seconds are expected, which silently lands you 50,000 years in the future. With no explicit unit, length is the practical heuristic:

  • 10 digits — seconds. 1735689600 is January 2025.
  • 13 digits — milliseconds. This is what JavaScript's Date.now() returns.
  • 16 digits — microseconds. Common in Postgres timestamptz dumps and Python's time.time_ns()/1000.
  • 19 digits — nanoseconds. Go's time.Now().UnixNano() lands here.

This tool detects the unit from the digit count and tells you which one it picked, so you can spot a mis-scaled value immediately.

The year 2038 problem

Timestamps stored as a signed 32-bit integer overflow at 03:14:07 UTC on 19 January 2038. MySQL's TIMESTAMP column, 32-bit time_t on older systems, and plenty of embedded devices are exposed. The fix is to widen the storage to 64 bits before that date arrives — a schema change most people postpone until it is urgent.

Working with timestamps in code

// JavaScript
Date.now();                        // ms
Math.floor(Date.now() / 1000);     // s
new Date(1735689600 * 1000).toISOString();

# Python
import datetime
datetime.datetime.now(datetime.timezone.utc).timestamp()
datetime.datetime.fromtimestamp(1735689600, datetime.timezone.utc)

// Java
Instant.now().getEpochSecond();
Instant.ofEpochSecond(1735689600);

Frequently asked questions

Why is my converted time off by exactly a whole number of hours?

Timezone, not the timestamp. Epoch values are UTC by definition; the "local time" row here applies your browser's configured zone, while the UTC row shows the raw instant. If they differ by 8 hours you are likely in UTC+8.

Does this account for leap seconds?

No, and neither does Unix time itself — leap seconds are deliberately ignored so that every day has exactly 86,400 seconds. For civil time that matters, use TAI or a time library with a leap-second table.

What is negative epoch time?

Timestamps before 1970. -86400 is 31 December 1969, 00:00 UTC. They are perfectly valid and supported here.

Should I store seconds or milliseconds?

Whichever your stack is consistent about — the bug is never the unit itself, it is mixing two. Seconds keep the value readable and fit in a 32-bit integer until 2038; milliseconds match JavaScript's native Date and avoid conversion on the client.
