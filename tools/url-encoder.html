encodeURIComponent versus encodeURI

These two functions are the source of most broken links, and the difference is simple once you see it laid out:

  • encodeURI leaves URL syntax characters alone — : / ? & = #. Use it on a complete URL you want to make safe.
  • encodeURIComponent escapes those characters too. Use it on a value you are about to put inside a query parameter or path segment.

The classic bug: passing a full URL through encodeURIComponent as a redirect target without the receiving server decoding it, which turns https://a.com/cb into https%3A%2F%2Fa.com%2Fcb and produces a 404. The reverse mistake — putting raw & or = into a query value — silently truncates your parameter.

What actually needs escaping

RFC 3986 defines a small set of unreserved characters that never need encoding: A–Z a–z 0–9 - _ . ~. Everything else is either reserved (has syntactic meaning) or unsafe. In practice you escape:

  • Spaces — as %20, or + in application/x-www-form-urlencoded bodies. This is why "Decode + as space" is a separate button here: the two conventions disagree.
  • Non-ASCII — UTF-8 bytes, each percent-encoded. 中 becomes %E4%B8%AD.
  • Reserved characters appearing as data rather than syntax — % itself, &, #, +.

Double encoding, the silent killer

If a string has already been encoded and you encode it again, %20 becomes %2520, because % itself encoded to %25. Nothing throws an error — the link just returns the wrong page, or a 404, and you spend an hour bisecting the request. If a decoded value looks like %25 where you expected a space, you have double-encoded.

Frequently asked questions

Why does my decoded text show garbled characters?

The bytes were not UTF-8. Older systems encode query strings as GBK, Latin-1 or Shift-JIS, and those byte sequences are not valid UTF-8, so the decoder substitutes replacement characters. There is no way to recover the original from the percent-encoded form alone without knowing the source encoding.

Is a + a space or a plus sign?

It depends on context, which is genuinely unfortunate. In a query string, + conventionally means space (from HTML form encoding). In a path segment, it is a literal plus. When in doubt, use %20 for spaces so there is no ambiguity.

Does encoding a URL make it secure?

No. Percent-encoding is purely syntactic. It does not protect against injection, and decoding it is trivial. Validate parameters server-side against an allowlist; never rely on encoding as a defence.
